## Symptom
After the structural-parser rewrite (#73), the decoder passed its entire test suite but failed to parse a real Copilot database: keys did not match and document protobufs did not unwrap, so collections came back empty or partial.

## How it was detected
Running the new parser against the maintainer's real database. The synthetic test database (built by the project's own test helpers) could not surface the problem because the fixture *and* the parser encoded the same wrong beliefs about the format.

## Root cause
Two shared error terms between fixture and code:
1. **Keys**: the parser (and the fixture generator) assumed LevelDB keys are simple path strings. The real Firestore SDK writes binary keys with marker bytes (`\x85`, `\x00\x01`, `\xBE`, `\x80`).
2. **Values**: the parser assumed bare Document protobufs with fields wrapped in a MapValue. The real SDK wraps documents in a `MaybeDocument` envelope and stores fields as direct map entries.

Tests validated the parser against the fixture generator's output — i.e., against itself.

## The fix
PR #74 rewrote the key parser for the real binary marker format, added `MaybeDocument` handling, and — the class-level part — added a **real-database integration test** that decodes the maintainer's actual cache and validates field mapping and collection counts (later gated behind `RUN_REAL_DB_TESTS=1`). It also added a temp-copy mechanism so the DB can be read while the Copilot app holds the LevelDB lock.

## Detector
The `RUN_REAL_DB_TESTS=1` real-database integration suite: any fixture/reality divergence in the decode path now fails against the genuine artifact, not the synthetic one. This is the earliest class-level detector in the repo's history for fixture-reality drift on the decode surface.

## Lesson
A fixture generated by the same mental model as the code under test proves consistency, not correctness. Every parser for an external format needs at least one test that consumes a genuine artifact produced by the external system.
